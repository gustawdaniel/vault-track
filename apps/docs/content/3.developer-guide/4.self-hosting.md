# Self-Hosting the Backend

VaultTrack is designed with a local-first architecture, but it relies on a central backend to synchronize events between your devices (e.g. desktop to mobile phone) and to proxy AI receipt scanning requests.

While the official application uses the `api.vaulttrack.org` backend by default, you can completely self-host your own synchronization server for maximum privacy and control.

## Prerequisites
- A remote server or VPS (e.g., DigitalOcean, Hetzner, AWS)
- Docker and Docker Compose installed
- A domain name (optional but recommended for SSL)

## Step 1: Deploying the Backend using Docker Compose

VaultTrack provides a `docker-compose.yml` file in the root of the repository to easily spin up the backend API, the database, and the Redis cache.

1. Clone the repository on your server:
   ```bash
   git clone https://github.com/gustawdaniel/vault-track.git
   cd vault-track
   ```

2. Create and configure your `.env` file manually, or by copying an existing template if available:
   ```bash
   nano .env
   ```

   **Environment Variables Configuration**
   
   Here is a breakdown of the variables you need to configure in your `.env` file:

   | Variable | Mandatory | Why it is needed | How to create/obtain it |
   | :--- | :--- | :--- | :--- |
   | `TURSO_DATABASE_URL` | Yes | Points to your SQLite database. | Use `file:/data/db.sqlite` to store it locally inside the Docker volume. |
   | `TURSO_AUTH_TOKEN` | No | Required only if you are using a remote Turso cloud database instead of the local SQLite file. | Generate a token from your Turso project dashboard. |
   | `ADMIN_EMAIL` | Yes | Specifies the email address of the admin user allowed to access the admin panel. | Your personal email address (must match the Google account you use to log in). |
   | `COOKIE_SECRET` | Yes | Used to securely sign authentication cookies. | Generate a strong random string (e.g., run `openssl rand -hex 32` in your terminal). |
   | `GOOGLE_CLIENT_ID` | Yes | Needed for Google OAuth login to the admin panel. | Create OAuth 2.0 Client credentials in the [Google Cloud Console](https://console.cloud.google.com/). |
   | `GOOGLE_CLIENT_SECRET`| Yes | Needed for Google OAuth login to the admin panel. | Comes alongside your Google Client ID from the Google Cloud Console. |
   | `GOOGLE_API_KEY` | Yes | Required to use the AI receipt scanning functionality. | Generate an API key from [Google AI Studio](https://aistudio.google.com/). |
   | `GEMINI_MODEL` | No | Specifies the AI model used for receipt scanning. | Can be left blank to use the default model (e.g., `gemini-1.5-flash`). |

3. Start the services:
   ```bash
   docker compose up -d
   ```

By default, the backend API will be exposed on port `4500` via HTTP.

> [!WARNING]
> **HTTPS is Required!** Browsers strictly enforce Mixed Content policies. If you are using the official VaultTrack frontend hosted on `https://vaulttrack.org` (or any other HTTPS domain), your browser will block all requests to an HTTP backend (e.g., `http://your-server-ip:4500`).
>
> You **must** set up a reverse proxy with an SSL certificate (like Nginx, Caddy, or Traefik) and point a domain name to your server to expose your backend over HTTPS.

## Step 2: Configuring the Frontend to use your Backend

Once your custom backend is running and secured behind HTTPS (e.g., `https://api.yourdomain.com/api`), you need to tell your VaultTrack frontend to use it.

1. Open the VaultTrack web application or desktop app.
2. Click on the **Settings** menu.
3. Select **Custom Backend**.
4. Enter your custom backend URL in the input field.
5. Click **Save Configuration**.

The app will reload, and all future synchronization requests, receipt analyses, and exchange rate fetches will be securely routed to your personal server.
